# M3 — Matching engine, matches UI, compatibility report

Goal: members who completed onboarding (including the M2 lifestyle questionnaire) see a calm,
explainable list of people they could live with, ranked by lifestyle compatibility, with a
compatibility report that shows — in plain language — where two people align and where they differ.
M3 ships `scoreCompatibility()` in `packages/shared`, `GET /api/v1/matches`, the Matches screen
(replacing the placeholder), and a seed script that fills staging with synthetic members so the
owner can exercise matching end-to-end. Chat stays in M4, rooms in M5, push in M6.

This file is also the milestone progress ledger. If work has to restart, read `CLAUDE.md`, then this
file, then continue from the first unchecked item. Do not assume chat history exists.

## Scope (M3 only)

- A pure, deterministic compatibility score over the 10 M2 lifestyle questions, grouped into the 5
  dimensions, with three explainable tiers from the mockups.
- Eligibility gates over existing logistics fields (seeking, budget, move-in window, area/campus):
  who may appear in your list at all. Gates never change the score.
- `GET /api/v1/matches`: session-authed, compute-on-read at test scale, sorted best-first.
- Matches screen: list cards (score, tier, habit tags, area) and a compatibility report (both sides
  per dimension, shared/friction points, logistics rows). Desktop gets the two-pane layout from
  mockup #1; mobile gets list → report panel.
- `scripts/seed-matches.mjs`: deterministic synthetic members across all 5 archetypes, inserted
  into **staging D1 only**, with a one-line cascading cleanup.
- All new copy lives in `apps/web/src/locales/en.json` + `el.json`; Greek is drafted natively and
  owner-reviewed before any tester sees it.

### Non-goals (M4+)

- Chat, icebreaker messages, "say hi" buttons (mockup #1/#3 affordances) — M4.
- Rooms, households, team-up groups — M5. Notifications — M6.
- Likes/passes/saving matches; mutual-match state; anything stored per pair. M3 computes on read.
- Photos of other members in the list (no public photo endpoint exists; needs its own privacy
  pass) — initials avatars in M3, endpoint decision in M4.
- A scheduled weekly matching batch. The `scheduled()` handler stays a stub; the stale "arrives in

- Graphical move-in timeline; text rows only.
- Changing `scripts/sim.mjs`.

## Compatibility model

### Score (pure, symmetric, integer 0–100)

Per question, distance `d = |a − b|` between the two answer levels (0/1/2):

| d   | weight |
| --- | ------ |
| 0   | 1.0    |
| 1   | 0.5    |
| 2   | 0.0    |

- `score = round(mean of the 10 weights × 100)` — every question counts 10%; no hidden weights
  (explainability is a product pillar).
- `dimensionScores[dimension] = round(mean of that dimension's 2 weights × 100)`.
- `sharedQuestions` = question ids where `d = 0`; `frictionQuestions` = ids where `d = 2`.
- Identical answers → 100; opposite on everything → 0; swapping the two people changes nothing.

### Tiers

| Tier id         | Threshold | English (badge + line)                                     | Greek (draft)                                                     |
| --------------- | --------- | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| strong-overlap  | ≥ 75      | Strong Overlap — "Your lifestyles line up on most things." | Ισχυρή Συμφωνία — «Οι τρόποι ζωής σας συμφωνούν στα περισσότερα.» |
| worth-a-chat    | 50 – 74   | Worth a Chat — "Enough in common to be worth a hello."     | Αξίζει μια Κουβέντα — «Αρκετά κοινά για να αξίζει ένα γεια.»      |
| likely-friction | < 50      | Likely Friction — "A few habits may clash at home."        | Πιθανή Τριβή — «Κάποιες συνήθειες μπορεί να τρίβονται στο σπίτι.» |

### Eligibility gates (who appears in your list)

A candidate appears only when **every** gate passes; missing data never fails a gate (defensive —
complete profiles always have these fields anyway). Gates are checked in code after a coarse SQL
prefilter (`user_id != me`, `lifestyle_json NOT NULL`, `onboarding_completed_at NOT NULL`,
`users.status = 'active' AND users.deleted_at IS NULL`).

1. **Not you**, onboarding complete (re-verified in JS via `isOnboardingComplete`), active account.
2. **Seeking**: the pair can actually share a home — at least one side `either`, **or** the two
   differ (`room` + `roommate`). Two `room`s or two `roommate`s are excluded (team-up is M5).
3. **Budget**: `[budgetMin, budgetMax]` ranges intersect (inclusive).
4. **Timing**: `[moveInFrom, moveInTo]` windows intersect (inclusive, calendar dates).
5. **Area**: `|Δlat| ≤ 0.05` **and** `|Δlng| ≤ 0.05` (stored coords are already coarsened to 2
   decimals; 0.05 ≈ central-Athens scale), **or** the same non-null `campusId`.

Sort: score desc, then `displayName` asc for stability. Limit 20. No pagination in v1.

The endpoint answers 403 `forbidden` ("Finish your profile to see matches.") for callers whose own
onboarding is incomplete.

### What the report shows (privacy scope)

Eligible matches see each other's lifestyle answers **at dimension level in the report** and as
derived habit tags in the list — never the raw questionnaire grid. The payload carries the 10 answer
levels so the client can render "You: label · Them: label" per dimension with the existing
`lifestyle.questions.*.options.*` strings; no new question copy is added. This is the M2 "only you
can see this **for now**" promise maturing: answers are shared exactly with people who pass your
gates and whose gates you pass. The profile card copy is updated to say so.

### Habit tags (derived from their answers; max 3 shown, question order)

| Tag id       | Rule                  | English               | Greek (draft)             |
| ------------ | --------------------- | --------------------- | ------------------------- |
| early-bird   | quiet-schedule = 0    | Early bird            | Νωρίς για ύπνο            |
| night-owl    | quiet-schedule = 2    | Night owl             | Αργά για ύπνο             |
| very-tidy    | clean-tidy = 0        | Tidies as they go     | Τακτοποιεί συνεχώς        |
| relaxed-tidy | clean-tidy = 2        | Tidies when needed    | Τακτοποιεί όταν χρειαστεί |
| home-cook    | kitchen-cooking = 0   | Cooks proper meals    | Μαγειρεύει κανονικά       |
| social-host  | social-gatherings = 2 | Often has people over | Συχνά κόσμος σπίτι        |

## API

`GET /api/v1/matches` — `requireSession` (same module pattern as `me.ts`/`campuses.ts`), mounted at
`/api/v1/matches` in `apps/worker/src/index.ts`.

- Response validated by `matchesResponseSchema` (shared, `.strict()`): `{ matches: MatchItem[] }`;
  `MatchItem` = `userId`, `displayName`, `areaLabel`, `lifeStage`, `seeking`, `budgetMin`,
  `budgetMax`, `moveInFrom`, `moveInTo`, `campusId`, `score`, `tier`, `dimensionScores`,
  `sharedQuestions`, `frictionQuestions`, `habitTags`, `lifestyleAnswers`.
- Errors use the shared `apiError` envelope: 401 `unauthorized`, 403 `forbidden` (incomplete
  caller). No query params, no new error codes.
- Candidate rows map through the existing `toProfileSnapshot`; scoring/gating call only pure shared
  functions. Nothing about matching is logged.

## Seeds (staging only)

`scripts/seed-matches.mjs` (`pnpm seed:matches`):

- Args `--count` (default 12), `--seed` (default 42), `--dry-run`. Deterministic (mulberry32, same
  pattern as `sim.mjs`); no new dependencies.
- Personas cover **all 5 archetypes** with hand-verified answer sets (expected archetype noted per
  persona and checked in the spec review); names are a bilingual Greek/international mix; emails
  `<slug>@seed.hearth.test`; user ids `seed_<slug>`; `emailVerified = 1`.
- Profiles: Athens-cluster coarsened areas (Koukaki, Exarcheia, Ambelokipi, Zografou, Patissia; a
  Zografou student set shares a campus), budgets €250–700 (step 50), move-in windows inside the
  next 12 months, `seeking` weighted to `roommate`/`either` so room-seekers see them.
- Writes generated SQL to a temp file and executes
  `corepack pnpm exec wrangler d1 execute hearth-db-staging --remote --env staging --file …` —
  the staging database is hardcoded; there is no prod target to fat-finger. `--dry-run` prints the
  SQL instead. Cleanup (one line, cascades via FK):
  `DELETE FROM users WHERE id LIKE 'seed_%';`
- Applied **after** the M3 deploy; verified by SQL row count + owner eyeballing `/matches`.

## Decisions (append-only; keep reasons)

- 2026-11-14 — Score = lifestyle only; logistics are eligibility gates, never score input. Reason:
  "82% and here's why" must be answerable in one sentence over the questionnaire; mixing rent
  arithmetic into it makes the number unexplainable.
- 2026-11-14 — Every question weighs 10%; tiers at 75/50. Reason: no hidden weights to defend; the
  thresholds place "all agree + one miss" at 95 and "opposite on a third" at ~67.
- 2026-11-14 — Compute-on-read; no stored per-pair state; `scheduled()` stays a stub (its stale
  "milestone 3" comments get corrected). Reason: at test scale a scan is trivial and always fresh;
  batching buys staleness and infra. Revisit at `MATCH_POOL_THRESHOLD` (500).
- 2026-11-14 — Eligible matches see each other's answers (dimension-level report + tags), nobody
  else; profile copy updated to say so. Reason: matching is the product's value exchange, and M2's
  "for now" copy already promised this moment.
- 2026-11-14 — No photos of others in M3 (initials avatars); a public photo endpoint needs its own
  privacy pass — M4, alongside chat which needs it more.
- 2026-11-14 — No like/pass, no icebreakers, no graphical timeline. Shared/friction chips are the
  icebreaker; move-in overlap is a text row. Calm over mechanics.
- 2026-11-14 — Seeds are marked (`seed_` ids, `@seed.hearth.test`), staging-only, deterministically
  regenerable, and cascade-deleted in one line. `sim.mjs` stays untouched.
- 2026-11-14 — Worker endpoint tests stay deferred (no session scaffolding exists; building it is
  M1-deferred scope). Shared unit tests cover scoring, gates, and tags exhaustively; the existing
  e2e smoke suite must stay green.

## Acceptance

- A complete member calling `GET /api/v1/matches` receives matches sorted by score desc, each with
  tier, dimension scores, shared/friction question ids, habit tags, and lifestyle answers; an
  incomplete caller gets 403; an unauthenticated caller gets 401.
- Identical lifestyles → 100 / Strong Overlap; all-opposite → 0 / Likely Friction; boundaries 74/75
  and 49/50 land in the right tier; scoring is symmetric (unit-tested).
- Every gate has unit tests: seeking matrix (room+room excluded, either passes everything), budget
  intersect/edge-touch/disjoint, window edge-touch/disjoint, area box ±0.05 boundary, campus
  fallback, null-passes-through.
- The Matches screen renders list + report bilingually, with empty/loading/error states, keyboard
  - screen-reader operable, usable at 360 px; two-pane at `lg`.

- `pnpm check:i18n`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm test:e2e`
  all pass; e2e placeholder assertions updated if they referenced the old Matches copy.
- No new dependencies; no new hex colors; nothing about members is logged.
