# M5 — Rooms: household listings

Status: draft for owner review (decisions table pending approval). Builds on
shipped M1–M4 (profiles, lifestyle, matching, 1:1 chat). Canonical visual
reference: `docs/design/mockups/10-rooms-and-groups.md` (Stitch #10).

## Context

The owner chose **Rooms only** for M5 (2026-11-15): members who have a spare
room post a household listing; everyone else browses and contacts the lister
through the M4 chat. Team-up groups (mockup #10 «Ψάχνουμε μαζί») are a separate
future milestone. The Rooms tab is the app's 4th bottom-nav tab.

## Goals

1. A member with a room can create one active household listing (title,
   description, area, rent, bills flag, available-from date, 0–3 photos),
   edit it, withdraw it, or delete it.
2. Every complete member can browse active listings (newest first) with a
   compatibility chip (lifestyle score vs. the lister), the lister's verified
   badge, and rent/area/availability chips.
3. A listing's details view reuses the M3 compatibility report layout against
   the lister, plus the full description and photos.
4. «Πες ένα γεια» on a listing opens the M4 conversation with the lister.
5. Matches gains a «Έχουν ήδη δωμάτιο» (has a room) filter chip.

## Non-goals

- Team-up groups, invite links, collective budgets (mockup #10 section 2) —
  future milestone.
- Requests inbox / «Αίτημα Γνωριμίας» system (mockup #11) — chat say-hi stands.
- Multi-member household entities (linked housemate accounts) — single lister,
  housemates described in free text.
- Notifications bell (M6), report/block (deferred), map views, saved searches,
  listing promotion, rent ranges (single monthly figure only).

## Decisions (owner-pending, flagged ⚑)

1. **Listing shape**: one active listing per member; `409 conflict` on a second
   create. Withdrawn listings keep their row (status flip) but disappear from
   browse; delete removes row + photos.
2. **Photos**: reuse the profile-photo pipeline (client JPEG re-encode, magic-
   byte sniff, metadata strip, ≤5 MB each). 0–3 per listing, stored under
   `rooms/<listingId>/<n>.jpg` in the existing R2 bucket. Served via
   `GET /api/v1/rooms/:id/photos/:n` (session required; the caller's own
   completeness is not re-checked — listing ids are only reachable through the
   complete-gated browse) — the first photo endpoint visible to members other
   than the owner. No photos ⇒ no upload
   step; the card shows a token-colored placeholder panel. ⚑
3. **Browsing eligibility**: any complete member sees all active listings —
   listing visibility is NOT gated by M3 match gates (a room is a room).
4. **Contact rule**: `POST /api/v1/chats` gains one exception — when the peer
   has an active listing, the M3 match gates are skipped (both members must
   still be complete + active). Rationale: inquiring about a room is not a
   lifestyle match; testers would otherwise hit confusing 403s on listings
   they can see. ⚑
5. **Compatibility chip**: `scoreCompatibility(viewer, lister)` + tier, shown
   on card and details (mockup «92% Ρυθμός»). Lister's raw answers never shown
   beyond the existing report format.
6. **Verified badge**: derived from `academic_email_verified_at` (existing).
7. **Vibe meters on card**: NOT shipped (they imply household-level aggregate
   data). The details view reuses the M3 per-dimension report instead.
8. **Nav**: 4 tabs — Matches / Rooms / Messages / Profile (mockup order).
9. **Sorting + limits**: newest first, limit 20 (MATCHES_LIMIT pattern); no
   search/filter in M5 beyond the matches-side "has room" chip.
10. **Areas**: listing area reuses the profile pattern (free label + coarsened
    lat/lng, 2 decimals); no exact addresses (privacy rule).
11. **Deletion**: `DELETE /api/v1/me` removes the member's listing rows (FK
    cascade) and R2 room photos explicitly (mirrors profile photo cleanup).
12. **Seeds**: `scripts/seed-rooms.mjs` inserts 4 listings owned by seed
    personas (no photos — placeholders; cleanup `DELETE FROM rooms WHERE id
    LIKE 'seed_%'`).

## Product design

- **Rooms tab** (`/rooms`, RequireAuth): header + households section header
  («Το σπίτι μας χρειάζεται ακόμα έναν» per the reference — EN: "Our place
  needs one more gentle soul") + card grid (1-col
  mobile, 2-col ≥lg). Empty state, loading, error states per house rules.
- **Room card**: photo strip (or placeholder panel), title, verified badge,
  area label, rent chip «340€/μήνα» (+ «συμπεριλαμβάνονται κοινόχρηστα» when
  bills included), availability chip «Από 1η Οκτωβρίου» (localized date),
  lister initials + name, compatibility chip (score + tier color).
- **Details** (bottom sheet mobile / side panel lg, reuse matches overlay
  plumbing): photos, full description, spec chips, M3-style compatibility
  report vs. lister, «Πες ένα γεια» (navigates `/messages?with=<listerId>` —
  the M4 say-hi path, idempotent).
- **Create/edit** (`/rooms/new`, own listing edit from Rooms tab): form with
  the fields above; photo picker (0–3) reusing the profile photo UX; withdraw
  / reactivate toggle; delete with a two-step inline confirm (calmer than the
  typed-DELETE pattern — a listing is lower-stakes than an account).
- **Matches filter chip**: client-side filter of the loaded matches list on
  `hasRoom` (MatchItem gains a boolean via the rooms join — no new request).
- **My listing card**: atop the Rooms tab when the member has one (status +
  title + Edit CTA; withdraw/reactivate/delete live in the edit screen).

## Data model

Migration `0005_rooms.sql`:

```sql
CREATE TABLE rooms (
  id TEXT PRIMARY KEY,                -- crypto.randomUUID()
  lister_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title TEXT NOT NULL,                -- 5–80 chars
  description TEXT NOT NULL,          -- 120–2000 chars
  area_label TEXT NOT NULL,
  area_lat REAL NOT NULL,             -- coarsened, 2 decimals
  area_lng REAL NOT NULL,
  rent_eur INTEGER NOT NULL,          -- 50–5000
  bills_included INTEGER NOT NULL DEFAULT 0,
  available_from TEXT NOT NULL,       -- YYYY-MM-DD
  photo_count INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','withdrawn')),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_rooms_status_created ON rooms(status, created_at);
CREATE INDEX idx_rooms_lister ON rooms(lister_id);
```

Drizzle table mirrors this in `apps/worker/src/db/schema.ts`.

## API

All under `/api/v1`, `requireSession`, same-origin, Zod-validated:

- `GET /rooms` → active listings newest first (limit 20): id, title, area,
  rent, billsIncluded, availableFrom, photoCount, status, lister summary
  (userId, displayName, verified), score + tier (computed vs. caller).
- `POST /rooms` → create (complete profile required; one active listing —
  `409 conflict`).
- `GET /rooms/:id` → details + lister lifestyle answers (report reuse);
  `404` unknown/withdrawn-for-others (owner sees own withdrawn via `/rooms/mine`).
- `GET /rooms/mine` → own listing incl. withdrawn (drives the Rooms tab card).
- `PATCH /rooms/:id` → edit own listing (fields + status flips).
- `DELETE /rooms/:id` → delete own listing + R2 photos.
- `POST /rooms/:id/photos` → multipart upload (sets/increments photo_count,
  max 3); `GET /rooms/:id/photos/:n` → serve bytes; `DELETE /rooms/:id/photos/:n`.
- `POST /chats` change per Decision 4 (listing-holder exception) — documented
  in M4.md via a note, code comment points here.

Shared schemas in `packages/shared/src/room.ts` (title/description/rent/date
bounds, room schemas, strict responses) with unit tests.

## Privacy & safety

- No exact addresses; coarsened coordinates only (unchanged rule).
- Room photos: same sniff/strip/re-encode as profile photos; no EXIF.
- No listing content in logs; no new third parties; CSP untouched.
- Contact still requires a signed-in complete member; chat rules (M4) apply
  after the thread exists (cooldown, eligibility file, purge on deletion).
