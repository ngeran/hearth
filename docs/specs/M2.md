# M2 — Lifestyle questionnaire

Goal: every member answers a short, calm lifestyle questionnaire so Hearth can describe how they
live at home. Answers are private, validated, versioned, and produce an explainable archetype the
member sees on their profile. The questionnaire is the data foundation the M3 matching engine
scores; M2 ships no scoring, no matches, and no compatibility report.

This file is also the milestone progress ledger. If work has to restart, read `CLAUDE.md`, then this
file, then continue from the first unchecked item. Do not assume chat history exists.

## Scope (M2 only)

- A 10-question lifestyle questionnaire: 2 questions per dimension across the 5 dimensions from the
  design mockups — Social Rhythm, Cleanliness, Kitchen Sharing, Quiet Hours, Guests & Partners.
- Every question has exactly 3 neutral options; answers are ordinal levels 0/1/2. No free text, no
  "right" answer, no protected-characteristic questions.
- A new onboarding step ("Lifestyle") between Living and Finish; answering is required to finish
  onboarding. The step saves once, all 10 answers together, via the existing profile patch.
- Profile page gains a "Your lifestyle" section: the five dimensions summarized in plain language,
  the derived archetype with a one-line description, and a way to change answers.
- Immediately after completing the questionnaire (onboarding and edits), the member sees the
  "What we learned about you" summary with the archetype — the moment of recognition from the
  mockups.
- Answers are visible only to their owner in M2. Nothing about lifestyle is shown to other members
  until the M3 compatibility report.
- All questionnaire copy lives in `apps/web/src/locales/en.json` and `el.json`; Greek is drafted
  natively and reviewed by the owner before any tester sees it.

### Non-goals (M3+)

- Scoring, matches, `GET /api/v1/matches`, compatibility report, icebreakers.
- Showing any lifestyle data to other members.
- Changing `scripts/sim.mjs`; its archetype list is reconciled with the real engine in M3.
- Notifications, chat, rooms.

## Archetype (derived, never stored)

`deriveLifestyleArchetype(answers)` in `packages/shared` is a pure function:

1. `socialScore = social-gatherings + social-weeknights` (0–4). Low ≤ 1, mid = 2, high ≥ 3.
2. `schedule = quiet-schedule` level (0 early, 1 balanced, 2 late).
3. Mapping:
   - late schedule and socialScore ≤ 2 → **Night Owl Haven** («Νυχτερινό Καταφύγιο»)
   - low social, early schedule → **Quiet Mornings** («Ήσυχα Πρωινά»)
   - low social otherwise → **Calm Sanctuary** («Γαλήνιο Καταφύγιο»)
   - mid social → **Steady Rhythm** («Σταθερός Ρυθμός»)
   - high social → **Open Door** («Ανοιχτή Πόρτα»)

Each archetype has a one-line description in both locales, shown with the summary. The rule is
explainable in one sentence on the screen ("based on your evenings and how often you have people
over"). Names are owner-reviewed before build sign-off.

## Decisions (append-only; keep reasons)

- 2026-11-14 — Ten fixed ordinal questions (2 per dimension, 3 levels each), all required, saved
  together. Reason: deterministic, explainable M3 scoring needs comparable data, not free text; ten
  questions keep completion under ~3 minutes (calm UX).
- 2026-11-14 — Answers stored as one nullable `lifestyle_json` TEXT column on `profiles` with a
  `json_valid` CHECK, envelope `{ "version": 1, "answers": { [id]: 0|1|2 } }`, validated by shared
  Zod on write and on read. Reason: M3 scores whole objects in JS, so per-question columns buy
  nothing; the version field lets questions evolve without destructive migrations.
- 2026-11-14 — Archetype is derived on read in `packages/shared`, never persisted. Reason: answers
  are the data; the archetype is presentation and must never go stale.
- 2026-11-14 — The questionnaire is required for onboarding completeness (`ONBOARDING_FIELDS`
  gains `lifestyle`). Existing complete profiles become incomplete exactly once and re-enter
  onboarding at the Lifestyle step. Accepted because staging holds only owner test accounts.
- 2026-11-14 — No new endpoints. Answers ride `PATCH /api/v1/me` (new `lifestyle` key, all-or-
  nothing) and `GET /api/v1/me`; data export includes them automatically via the profile snapshot.
- 2026-11-14 — Question and option copy lives only in the locale files; ids and levels are code.
  Reason: equal EN/EL quality is a product principle; the i18n parity check enforces key sets.

## Acceptance

- A new member hits the Lifestyle step in onboarding, cannot continue until all 10 are answered,
  and sees the "What we learned about you" summary with archetype before finishing.
- An existing (pre-M2) complete profile is routed to the Lifestyle step once, then is complete
  again; previously answered fields are untouched.
- `PATCH /api/v1/me` with `lifestyle` rejects missing questions, unknown ids, out-of-range levels,
  and unknown keys; valid patches round-trip through `GET /api/v1/me` and the export payload.
- Changing answers later updates the summary and archetype; no stale copies anywhere.
- `pnpm check:i18n`, `pnpm typecheck`, `pnpm lint`, `pnpm test` (including new shared unit tests
  for the schema edges and every archetype branch), `pnpm build` all pass.
- Radio groups use fieldset/legend per dimension; fully keyboard operable; usable at 360 px;
  screen-reader labels verified. Empty/loading/error states for the profile section.
- Worker and Playwright tests remain deferred per the M1 decision; record any new gaps here.
