# M6 — Web Push Notifications

Status: draft for owner review (decisions table at the end). M6 is the final milestone
before the 8-tester round. Scope: quiet, privacy-by-default push notifications for new
1:1 chat messages. Everything else stays out (see Non-goals).

## Problem

Members only learn about new messages when they open the app. For a roommate-search
tool used a few times a day, a calm "someone wrote to you" nudge is the missing loop
closer — but it must respect the calm-technology and privacy-by-default pillars: no
engagement mechanics, no message bodies on lock screens, opt-in only.

## Goals

1. A member can turn on notifications from Profile → Notifications (browser permission
   prompt fires only from that explicit gesture).
2. When a 1:1 chat message is sent and the recipient has an active subscription and has
   not already read the message, exactly one push is delivered: sender name, no body.
3. Tapping the notification opens the conversation (`/messages?with=<senderId>`).
4. Subscriptions are per-device, pruned when the push service says they are gone, and
   deleted with the account.
5. The PWA's manual, non-blocking update contract survives the service-worker change.

## Non-goals

- Notification bell / inbox UI, unread badges.
- Quiet hours, per-thread muting, notification preferences beyond on/off.
- Pushes for matches, listings, or anything that is not a 1:1 chat message.
- Local-dev push testing (devOptions stays off; push is exercised on staging).
- Email fallback, badges/sounds beyond the OS default, DLQ infrastructure.

## Architecture

```
sender → POST /api/v1/chats/:peerId/messages
           └─ (existing DO send + D1 bump) … waitUntil(JOBS.send(job))
                                        │
worker queue() consumer  ←──────────────┘
  1. job {recipientId, senderId, senderName, threadLow, threadHigh}
  2. ChatRoom /state as recipient → skip if last.seq <= myRead (already read)
  3. load recipient subscriptions (D1) + recipient profile language
  4. for each subscription: generatePushHTTPRequest → fetch(endpoint)
     410/404 → delete subscription row
```

The unread check makes the common "recipient is actively chatting" case silent: their
read marker is caught up, so no push. The check runs at consume time (seconds after
send), which is the honest approximation without presence infrastructure.

## Library — webpush-webcrypto (decision 3)

`webpush-webcrypto@1.0.5` — MIT, zero dependencies, pure WebCrypto, BYO `fetch`. Chosen
over `web-push` (still not officially Workers-supported — open issue web-push#718) and
over hand-rolling RFC 8291/8292 (easy to get wrong; the library is community-verified
on Workers). No bundled TS types → local `declare module` shim in the worker. One-line
dependency justification lands in CLAUDE.md's decisions log.

- VAPID keys: generated once via `scripts/generate-vapid-keys.mjs` (uses the library's
  `ApplicationServerKeys.generate()`); `VAPID_PUBLIC_KEY` + `VAPID_SUBJECT` are
  non-secret vars, `VAPID_PRIVATE_KEY` is a wrangler secret. Key encoding is exactly
  whatever `toJSON()/fromJSON()` use (verified against the installed package in build
  step 3). `.dev.vars.example` gains the key list.
- Payload: `JSON.stringify({ url: "/messages?with=<senderId>" })` — no body, no name
  inside the payload (name goes in the localized notification title/body generated by
  the consumer from the recipient's profile language).

## Service worker — generateSW → injectManifest (decision 4)

`vite.config.ts` moves to `strategies: "injectManifest"` with `src/sw.ts`. The custom
worker keeps the existing contract: `precacheAndRoute(self.__WB_MANIFEST)` +
`cleanupOutdatedCaches()` + `clientsClaim()` + SKIP_WAITING message handler (update
prompts stay manual via the existing `registerSW({ onNeedRefresh })` flow — `skipWaiting`
is only called when the user accepts the prompt). Adds:

- `push` listener → `showNotification(payload.title, { body: payload.body, icon, badge, data: { url } })`. The payload the consumer encrypts is `{ title, body, url }` — localization happens server-side (recipient's profile language) before encryption; the SW only renders.
- `notificationclick` → focus an existing window client on the URL, else `openWindow`.

New web dependency: `workbox-precaching` (bundled into the SW only) — required by
injectManifest for `precacheAndRoute`. CSP/`_headers` already allow `worker-src 'self'`.

## Data model

Migration `0006_push_subscriptions.sql`:

```sql
CREATE TABLE `push_subscriptions` (
  `endpoint` text PRIMARY KEY,          -- push service URL, natural key
  `user_id` text NOT NULL REFERENCES `users`(`id`) ON DELETE CASCADE,
  `p256dh` text NOT NULL,               -- base64url client public key
  `auth` text NOT NULL,                 -- base64url auth secret
  `created_at` integer NOT NULL,
  `updated_at` integer NOT NULL
);
CREATE INDEX `idx_push_subscriptions_user` ON `push_subscriptions` (`user_id`);
```

One row per device. Re-subscribing upserts on the endpoint PK. Account deletion: rows
cascade with the user; an explicit delete in the `me.ts` purge block matches house style.

## API

All under `/api/v1/me/push`, `requireSession`, Zod-validated, shared schemas in
`packages/shared/src/push.ts` (+ tests):

- `GET /api/v1/me/push/key` → `{ publicKey }` (503 `service_unavailable` when the var
  is unset, so the UI can show "not configured yet" instead of failing silently).
- `POST /api/v1/me/push` `{ endpoint, keys: { p256dh, auth } }` → upsert, `204`.
- `DELETE /api/v1/me/push` `{ endpoint }` → delete own row (404 if not owned), `204`.

## Web UI

`NotificationsCard` in Profile (between Passkeys and the data section), all states
EN/EL (`notifications.*` locale block, ~14 keys):

- Unsupported (no `serviceWorker`/`pushManager`/`Notification`) → calm explainer.
- Default → "Turn on notifications" button (the permission gesture).
- Permission denied → instructions to re-enable in browser settings.
- Enabled → status line + "Turn off" (DELETE row + `pushManager.unsubscribe()`).
- Enable flow: `Notification.requestPermission()` → `getRegistration()` →
  `pushManager.subscribe({ applicationServerKey })` (key from `GET /key`) → POST.
- Never auto-prompts; never blocks anything.

## Queue configuration

Both `wrangler.jsonc` consumers (top-level + staging) gain `max_retries: 3`. No DLQ:
after retries the job is dropped; the consumer logs failure counts without PII
(never endpoints, keys, or names).

## Decisions for the owner

| #   | Decision            | Recommendation                                                                           |
| --- | ------------------- | ---------------------------------------------------------------------------------------- |
| 1   | Trigger scope       | New 1:1 chat messages only — nothing else pushes in M6                                   |
| 2   | Lock-screen privacy | Sender name only; message body never leaves the server                                   |
| 3   | Dependency          | Add `webpush-webcrypto` (zero-dep, WebCrypto, Workers-verified); reject `web-push`       |
| 4   | SW strategy         | generateSW → injectManifest (custom `sw.ts`); manual update prompts preserved            |
| 5   | VAPID management    | Owner-generated keys; public key + subject as vars, private key as secret                |
| 6   | Delivery semantics  | One push per message; unread-gated at consume time; 3 retries; dead subscriptions pruned |
