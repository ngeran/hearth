# M4 — 1:1 chat

Status: approved · Written 2026-11-14 · Builds on M3 (shipped in `0f663f0`).

Chat is the first feature that touches the Durable Object scaffold (`apps/worker/src/chat-room.ts`, binding `CHAT`, SQLite-backed class `ChatRoom`). Two people who can see each other in Matches can open one conversation and exchange text messages. Everything else stays out.

## Summary

- "Say hi" from a compatibility report opens (or creates) the 1:1 thread with that person.
- `/messages` becomes a real screen: thread list on the left (mobile: a list), conversation view with a composer.
- Messages are stored only inside the ChatRoom Durable Object — never in D1, never logged.
- Account deletion purges every conversation the account was part of.
- Transport is REST with short polling — no WebSockets in M4.

## Goals

1. A member can start a chat with anyone currently in their matches list, and only with those people.
2. A member can read and send text messages (1–1000 characters) in that thread, bilingual UI, from phone or desktop.
3. The thread list shows who you talk to, newest activity first, with an unread indicator.
4. Message bodies never touch D1, logs, or any third party; deletion removes them completely.
5. Calm UX: no typing indicators, no online dots, no notification noise. Polling pauses when the tab is hidden.

## Non-goals (explicit)

- WebSockets / server push (revisit only if polling demonstrably hurts; not expected at 8-tester scale).
- Typing indicators, read receipts rendered in UI, presence, online status.
- Like/pass or any stored pair state — chat eligibility is computed from the same M3 gates on demand.
- Block/report/moderation flows (safety screens are a later milestone; see Decisions).
- Group chats, rooms chat (M5), media attachments (photos in chat), voice.
- Message editing/deletion for the sender; "clear conversation for me".
- Nav-badge unread counts (the list shows unread; the badge can come with push in M6).
- Web push notifications (M6).
- Exporting message bodies in the data export (see Decisions — flagged to owner).

## Decisions

1. **Transport: REST + polling.** GET messages polls every 5 s while the tab is visible (TanStack Query `refetchInterval` gated on `document.visibilityState === "visible"`). Simpler than WS on both sides (no reconnect/heartbeat client code, no hibernation API surface), testable with plain `fetch`, adequate for the tester round. WS stays a non-goal until proven necessary.
2. **One conversation per pair, keyed deterministically.** `chatThreadId(a, b)` = `` `chat:${low}:${high}` `` with `low`/`high` being the lexicographically sorted user ids. `env.CHAT.idFromName(...)` gives both members the same room; no thread id needs to be invented or stored on the client.
3. **Bodies live only in the DO.** Message rows are DO-storage KV entries (`m:<zero-padded-seq>` → `{author, body, ts}`). D1 keeps only thread metadata (the pair, timestamps) so the thread list and account deletion can find conversations. Even the "last message preview" shown in the list is fetched live from the DO at list time, so no body derivative is persisted in D1.
4. **Auth at the route, identity forwarded.** `requireSession` runs in the Hono route; the route forwards the verified user id to the DO in an internal header (`x-hearth-user-id`). The DO namespace is not publicly reachable (same-script binding, `run_worker_first: ["/api/*"]`), so trusting the worker's own header is safe. The DO never parses cookies and never sees the session.
5. **Eligibility: current matches only.** `POST /api/v1/chats` recomputes the M3 gates server-side (self/complete/active, seeking pair, budget, window, area) for the caller + peer. If the peer is not currently match-eligible, no thread. If eligibility later ends, the existing thread stays readable (people keep their history) but this is an accepted edge at tester scale.
6. **D1 `chat_threads` table (migration 0004).** `user_low`/`user_high` (sorted pair, composite PK), `created_at`, `updated_at` (bumped on each message, drives list ordering). FKs cascade on user deletion; the deletion handler purges the DO first, then deletes rows.
7. **Read tracking in the DO.** `read:<userId>` = highest seq the user has seen; the messages GET updates it. Unread = `last.seq > read` per thread. Rendered as a dot in the list only — no receipts in the conversation.
8. **Send cooldown: 1 s per sender, enforced in the DO** (in-memory last-send timestamp; DO restart resets it, which is acceptable). Abusive-volume protection beyond that is a later milestone; the shared `rate_limited` error code is reused.
9. **Deletion purges chats.** `DELETE /api/v1/me` gains a step: for every `chat_threads` row involving the user, call the DO's purge endpoint (full `storage.deleteAll`), then the existing D1/R2 cleanup removes the rows via cascade. No body is ever passed through the worker in the purge path.
10. **Message export stays out of M4** (owner-flagged). The data export keeps covering profile data; adding a per-thread messages dump is real work (pagination, size) and nobody asked for it yet. Deletion (the privacy-critical half) is in scope.
11. **Block/report is not in M4.** For the closed tester round the moderation surface is: stop replying + account deletion. The Stitch Report/Block screens stay future work alongside the wider safety pass.
12. **Privacy pass from M3 lands here.** No logging of message bodies anywhere (worker route logs only request ids/codes as today); no new third-party code; the strict CSP is untouched (REST only); previews never persisted in D1 (Decision 3).
13. **Greek copy is written natively** for every new screen, same informal «σου» register as M2/M3.

## Data model

### D1 — `chat_threads` (migration `0004_chat_threads.sql`)

```sql
CREATE TABLE chat_threads (
  user_low   TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  user_high  TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_low, user_high)
);
CREATE INDEX idx_chat_threads_user_high ON chat_threads(user_high, updated_at);
```

(`user_low` index comes free with the composite PK: list query is `WHERE user_low = ? OR user_high = ?` ordered by `updated_at DESC`.)

### ChatRoom DO — storage keys

| Key                 | Value                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `meta`              | `{ userLow, userHigh }` (written once on first contact)                                    |
| `seq`               | integer, last assigned message sequence                                                    |
| `last`              | `{ seq, author, body, ts }` — powers list previews + unread without listing                |
| `m:<000000000000>`  | one message `{ author, body, ts }` (12-digit zero-padded seq → KV list order = chat order) |
| `read:<userId>`     | highest message seq this user has seen                                                     |
| `cooldown:<userId>` | last-send unix ms (in-memory only in practice; persisted for restarts)                     |

DO endpoints (fetch targets, all internal): `POST /send` `{body}` → message; `GET /list?after=<seq>&limit=50` → messages ascending + `last`; `GET /state` → `{last, myRead}` for list screen; `POST /read` `{seq}`; `POST /purge` (internal header check). All replies use the shared API envelope; all bodies validated with Zod from `@hearth/shared`.

## API (all under `/api/v1`, session required)

| Route                                     | Behavior                                                                                                                                                                                                                             |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /chats`                              | My threads, newest `updated_at` first. For each: peer profile summary (displayName, areaLabel, initials), unread flag, last message preview + ts — preview via per-thread DO `state` call (N stub calls, N ≤ 20). Empty list → `[]`. |
| `POST /chats` `{peerId}`                  | Recompute M3 eligibility for (me, peer). Not eligible/complete/active → 403 `forbidden`. Else upsert D1 row + touch DO `meta`, return the thread. Idempotent.                                                                        |
| `GET /chats/:peerId/messages?after=<seq>` | Forward to DO `list`; also updates my read marker to the returned max seq. 404 `not_found` if no thread exists for the pair.                                                                                                         |
| `POST /chats/:peerId/messages` `{body}`   | Validate `messageBodySchema` (1–1000 chars after trim, no control chars); DO enforces cooldown → 429 `rate_limited`. Bumps D1 `updated_at`. Returns the stored message.                                                              |

Peer profile summary in `GET /chats` reuses profile columns already selected by the matches route; no new personal data is exposed beyond what matches already show.

## Web UI

- `/messages` (replaces PlaceholderPage, wrapped in `RequireAuth`):
  - Thread list: rows with initials avatar, display name, area, last message preview (single line, truncated), relative time, unread dot. Empty state points to Matches («Ξεκίνα από τα ταιριάσματα»).
  - Conversation: header with peer name (back button on mobile), message list (own messages right-aligned, primary-tinted; theirs left, surface), day separators optional (skip in M4), composer (textarea autosize ≤ 4 rows, Enter sends on desktop, Shift+Enter newline; Send button), sending/disabled states, 1000-char counter past 900.
  - Polling: messages query `refetchInterval: 5000` while visible; threads query refetches on window focus + after send.
  - Layout: mobile single pane with push-navigation between list and thread; desktop (`lg:`) two-pane like Matches (list + sticky conversation). Works at 360 px.
- Compatibility report gains a **«Πες ένα γεια» / "Say hi"** button (primary, below the report title block): navigates to `/messages?with=<userId>`; the messages route creates the thread (idempotent) and focuses the composer. No auto-prefilled text (calm UX).
- States everywhere: loading (`common.loading`), error (`common.errorTitle/errorBody/retry`), empty thread list, empty conversation («no messages yet — say hi»), failed send (inline retry, message kept in composer).
